Why Specs Matter — Then and Now

The developer changed. So the specification had to change.

Specifications are not new. What is new is who reads them. For thirty years the reader was a human developer who could ask questions. Today the first reader is an AI agent that writes hundreds of lines a minute — and fills every gap with a silent guess.

1990s – 2000s · WATERFALL

The big document era

Business analysts wrote a BRD, then an FRD, then an SRS — often 100–200 pages — and handed them to developers who built for months. Gaps were filled in meetings and at the analyst's desk. Documents went stale the day coding started.

2001 – 2020 · AGILE

The conversation era

"Working software over comprehensive documentation." Specs shrank to user stories and acceptance criteria. The real detail lived in conversations and in the team's memory — which worked, because the developer was a person in the room who could ask "what did you mean?".

2023 → NOW · AI AGENTS

The spec-driven era

An agent like Cline writes the code in minutes. It was not in your meeting, it forgets between sessions, and it rarely asks — it assumes. The spec is now the main input to the build: short, layered, precise, version-controlled next to the code, and reused to regenerate code and tests.

  • Plant analogy. A spec is a Standard Operating Procedure. A new operator follows the SOP exactly; a vague SOP gives inconsistent product. Cline is an extremely fast new operator who never asks a question — so the SOP must be exact.
  • Why it matters even more for ML. An ML spec must fix things an app spec never needed: which data and labels, how it is split, which metric, what score is "good enough" (the quality gate), and the exact input and output of the prediction service. In today's Lab 1 prompt you will see lines like 80% train / 20% test, seed 42, exit if accuracy < 0.70 and {"image": "<base64>"} — each one a decision the agent must not invent.
  • Your role changes. You no longer have to type every line. You specify clearly, review what the agent produces, and validate it against the acceptance criteria. That is the skill this program is building.
The Failure Mode

One enormous document that answers everything, badly

The instinct is to write a single, exhaustive specification. It fails for a specific, mechanical reason — not because people are lazy, but because retrieval and review both break at that size.

The 200-page specification

  • Business context buried beside endpoint definitions
  • Nobody reads it end to end — including the agent
  • A change to one API forces a rewrite of the whole file
  • Retrieval pulls in 190 irrelevant pages
  • Review becomes impossible, so review stops happening

What actually helps

  • Small documents, each with one job
  • Ambiguity removed progressively, stage by stage
  • Version-controlled alongside the code
  • Retrievable in isolation — the agent reads only what it needs
  • Reviewable in one sitting by one person

The question is never PRD or FRD or SRS. It is which question this particular file is answering.

Do not write everything down.

Reduce ambiguity progressively.

Each layer takes the output of the one above it and makes one more category of decision explicit. By the time you reach implementation tasks, there is nothing left for the agent to guess — and nothing was written twice.

Our Two Days

One path, walked twice — first guided, then as a team

You practise the full journey on a simple image classifier, then repeat it on your own plant problem. Each step builds on the one before; nothing is thrown away.

Lab 1 · Individual · your laptop

Spec → vibe code → deep learning

  1. Install Cline, connect it to the class model
  2. Paste the spec-driven prompt: Cline writes the spec, code and tests
  3. Train and test on your laptop
  4. Learn DL by watching it: loss, train vs test, confusion matrix, confidence
  5. Experiments: 1 epoch, from scratch, an unknown class
Output: a working, tested classifier and a validation report
Lab 2 · Individual · laptop + Azure

From laptop to production

  1. Create your GitHub repository and push
  2. Upload images as a versioned Data asset
  3. Train + test as an Azure ML job; register the model
  4. Deploy a live endpoint; call it from a small app
  5. Build a 3-step pipeline: prep → train → evaluate
  6. Azure DevOps: add a new class, watch it retrain and redeploy
  7. Monitor: requests, latency, errors, prediction logs
Output: a live, versioned, self-updating model

Why it's built this way

  • Nothing to install except Cline. The model runs as a managed Azure deployment — no GPU on your laptop.
  • An Azure endpoint, not a public consumer AI site. Easier to allow on corporate networks, and your prompts stay inside the program's Azure subscription.
  • The same model for every lab. What works in Lab 1 works the same way in the capstone.
One class, one model

Share it fairly and it stays fast for everyone.

The whole room uses the same model deployment. A few habits keep it responsive:

  1. A new Cline task for each job. Smaller context means a faster answer for you and more capacity for everyone else.
  2. Small, specific tasks. "Implement evaluate.py as specified" beats "build everything again".
  3. If you see "429" or "rate limit", wait a moment and retry — do not click retry ten times.
  4. Never paste secrets or confidential plant data into a prompt.

Cline is not short of capability.

It is short of decisions you have not yet made.

Every KPI you benchmarked on Day 1 — specific energy consumption, potline current efficiency, cast & rolling yield — is a decision waiting to be written down as a value, not an adjective. You just did exactly that for the potline energy alert above — and your capstone does it for your own Day-1 KPI.
